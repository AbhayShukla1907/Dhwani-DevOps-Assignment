# Part D — Pipeline Review

## 5.1 Review of the Deployment Pipeline

I reviewed the workflow as a pull request reviewer. I have separated the findings into **blocking issues**, **non-blocking comments**, and items that are **fine as they stand**.

---

# 🔴 Blocking Issues

## BLOCKER 1 — Registry credential is exposed in the workflow log

The following code is unsafe:

```yaml
env:
  REGISTRY_TOKEN: ${{ secrets.REGISTRY_TOKEN }}
run: |
  echo "Authenticating with token $REGISTRY_TOKEN"

  The registry token is being explicitly passed to the shell and then printed using echo.

Even though the value comes from GitHub Secrets, credentials should never be deliberately written to CI logs.

Requested change

Remove the echo statement and authenticate using a mechanism that does not expose the credential.

For example, Docker authentication should pass the credential through the appropriate secure input mechanism rather than printing it.

I would block the merge until this is fixed.

BLOCKER 2 — Test failures are being ignored

The workflow contains:

pytest tests/ || true

The || true causes the shell command to succeed even when pytest returns a failure.

This means the workflow can continue to:

Build → Test fails → Workflow still green → Push → Deploy

A failing test therefore provides no protection against deploying broken code.

Requested change

Run:

pytest tests/

and allow a non-zero exit code to fail the workflow.

If a specific test is intentionally allowed to fail, that exception should be explicitly documented rather than suppressing every test failure.

I would block the merge until test failures correctly fail the pipeline.

BLOCKER 3 — Production image uses only the mutable latest tag

The image is built as:

docker build -t registry.example.com/grants:latest .

and pushed as:

docker push registry.example.com/grants:latest

Using only latest makes the production artifact ambiguous.

There is no direct way to determine which Git commit produced the image currently running in production. It also makes rollback less reliable because latest can point to a different image later.

Requested change

Tag the image using an immutable identifier such as the Git commit SHA:

docker build -t registry.example.com/grants:${GITHUB_SHA} .
docker push registry.example.com/grants:${GITHUB_SHA}

Production should deploy that exact image tag.

A human-readable release tag can also be added, but the production deployment should have an immutable reference.

I would block the merge until the production artifact is uniquely identifiable.

BLOCKER 4 — The deployment does not clearly deploy the exact image tested by CI

The production step executes:

ssh deploy@prod.example.com \
  "cd /srv/grants && docker compose pull && docker compose up -d"

The workflow does not pass the exact image version produced by the build to the production environment.

Combined with the use of:

registry.example.com/grants:latest

the image pulled by production can be different from the artifact that was tested earlier in the pipeline.

This breaks the important principle that the artifact tested by CI should be the same artifact deployed to production.

Requested change

Build and push an immutable image tag, then explicitly deploy that same tag.

The deployment configuration should receive the image version generated by CI rather than resolving a moving latest tag.

I would block the merge until this is made reproducible.

🟡 Non-blocking Comments
COMMENT 1 — Pin the checkout action

The workflow currently uses:

- uses: actions/checkout@master

I would recommend changing this to a stable version:

- uses: actions/checkout@v4

For stronger supply-chain reproducibility, the action can also be pinned to a reviewed commit SHA.

I would raise this as a non-blocking improvement rather than blocking solely because of it.

COMMENT 2 — Add an explicit registry login

The workflow defines:

REGISTRY_TOKEN: ${{ secrets.REGISTRY_TOKEN }}

but the shown workflow does not actually perform a registry login before:

docker push registry.example.com/grants:latest

I would add an explicit authentication step using the registry's supported secure authentication method.

The exact command depends on the registry implementation.

COMMENT 3 — Add deployment health verification

The deployment currently ends after:

docker compose up -d

A successful Docker command does not prove that the application itself is healthy.

I would recommend adding a post-deployment health check, for example:

curl --fail https://grants.example.gov/health

or another application-specific readiness endpoint.

If the health check fails, the deployment should be considered unsuccessful and trigger the appropriate rollback or alerting procedure.

COMMENT 4 — Separate CI validation from deployment

The current workflow puts build, testing, image push and production deployment into one job.

A clearer pipeline would separate these responsibilities:

Checkout
   ↓
Build
   ↓
Test
   ↓
Push immutable image
   ↓
Deploy
   ↓
Health check

This is easier to review and makes the production boundary clearer.

I would raise this as an improvement rather than a reason to block the current merge.

🟢 Fine As It Stands
1. Deployment is restricted to main

The workflow uses:

on:
  push:
    branches: [main]

This prevents arbitrary feature branches from automatically deploying to production.

For this assignment and a simple production pipeline, this is a reasonable choice.

I would leave this unchanged.

2. GitHub-hosted runner is appropriate

The workflow uses:

runs-on: ubuntu-latest

A GitHub-hosted runner is reasonable for this scale and avoids unnecessary operational overhead from maintaining a self-hosted runner.

I would leave this unchanged.

3. Building the Docker image in CI is correct

The workflow builds the application image in CI:

docker build -t registry.example.com/grants:latest .

The problem is not that the image is built in CI.

The issue is the use of the mutable latest tag and the lack of a clearly controlled artifact promotion process.

The general approach of building the image in CI should remain.

4. Docker Compose is reasonable for this deployment

The production server uses:

docker compose pull
docker compose up -d

For the scale described in the assignment, Docker Compose is a reasonable deployment mechanism.

There is no justification here for introducing Kubernetes, service meshes or another orchestration platform.

I would leave Docker Compose in place.

Overall Review Decision

I would block the merge because:

The registry credential is deliberately exposed in the workflow log.
Test failures are ignored with || true.
The production image uses the mutable latest tag.
The deployment does not guarantee that the exact tested artifact is the artifact deployed to production.

I would raise, but not block on:

Pinning actions/checkout.
Adding an explicit registry login.
Adding a post-deployment health check.
Separating CI validation from deployment.

The following are reasonable and should remain:

Deploying only from main.
Using a GitHub-hosted runner.
Building the Docker image in CI.
Using Docker Compose for this deployment.

The key principle I would enforce is:

Build once, test that exact artifact, deploy that exact artifact, and make the deployment identifiable and reversible.
